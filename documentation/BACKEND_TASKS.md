# Что передать бэкендеру перед демо SmartGuide

26 ноября 2026. База реализации: коммит `66d53ca`, ветка `feat/ai-provider-routing`. Этот документ ставит следующие задачи; незакрытые пункты ниже не являются готовыми функциями.

Цель ближайшей итерации: турист на телефоне вводит города, дни, USD и интересы → получает серверный план → открывает место на карте → задаёт вопрос или отправляет фото объекта пилота → получает ответ Groq и озвучку Gemini → настоящее взаимодействие появляется в PostgreSQL и панели. Для выбранного маршрута команда подтверждает источники и цены. Это критерий готового демо, а не обещание победы на хакатоне.

## С чего начать

В чистом checkout бэкендер может создать свою ветку от последней версии:

```powershell
git fetch origin
git switch -c feat/backend-demo origin/feat/ai-provider-routing
npm ci
npm run build:shared
npm run test --workspace=@smartguide/api
```

Серверные переменные и проверка провайдеров: [AI_BACKEND_HANDOFF.md](AI_BACKEND_HANDOFF.md). Существующие payload/response: [API_CONTRACT.md](API_CONTRACT.md). Изменения возвращать своей веткой и PR; чужие ветки не переписывать.

## P0: блокирует сквозное демо

### B01. Поднять отдельную PostgreSQL и отделить seed контента от демо-аналитики

**Владелец:** Backend. **Файлы:** [index.ts](../apps/api/src/index.ts), [db/index.ts](../apps/api/src/db/index.ts), [seed.ts](../apps/api/src/db/seed.ts), [schema.ts](../apps/api/src/db/schema.ts).

Сейчас `AUTO_SEED` по умолчанию включён. `seedDatabase()` обновляет досье и добавляет `INITIAL_ANALYTICS_SEED`, когда таблица interactions пуста. Поэтому успешный запуск может показать придуманные взаимодействия как обычную аналитику.

Сделать раздельные операции для загрузки контента и явно обозначенных демонстрационных событий. Для среды с реальными тестировщиками задать `AUTO_SEED=false`, подготовить схему и загрузить только проверенный контент отдельной процедурой. Для уже заполненной общей базы сначала определить происхождение записей; массовое удаление не является частью задачи. Текущий `db:push` использует `--force`: для общей базы подготовить и проверить план изменения схемы отдельно.

**Приёмка:** новая тестовая база содержит объекты, но 0 взаимодействий; повторный старт API не создаёт события и не перезаписывает утверждённый контент; `/api/health` сообщает `database: connected`; реальный вопрос создаёт одну новую запись. Демо-метрики, если нужны, находятся в отдельной явно обозначенной среде.

### B02. Проверить полную HTTP-цепочку гида и поведение при отказе DB

**Владелец:** Backend + AI. **Файлы:** [guide.routes.ts](../apps/api/src/routes/guide.routes.ts), [landmark.service.ts](../apps/api/src/services/landmark.service.ts), [analytics.service.ts](../apps/api/src/services/analytics.service.ts).

Прогнать `/api/landmarks`, `/api/landmarks/:slug`, `/api/guide/ask` и `/api/analytics/summary` с настоящей PostgreSQL. Сервис landmarks сейчас подставляет JSON при пустом результате, но ошибка самого DB-запроса до этого fallback не доходит. Выбрать явное поведение при недоступной DB: документированный 503 либо обозначенный режим локального досье. Не заявлять успешную запись аналитики при её отказе.

**Приёмка:** текстовый вопрос возвращает `sourceMode: groq-rag`, корректный объект и сохранённый `interactionId > 0`; при `includeAudio:true` есть воспроизводимый WAV; фото объекта пилота возвращает точный slug; постороннее/неопознанное фото без выбранного slug не подменяется первым объектом. В отдельном тесте отключённая DB даёт согласованный ограниченный по времени ответ. Если ответ гида сохранён без записи события, это явно отличимо от успешной аналитики, а не выдуманный ID.

### B03. Согласовать общий тайм-аут запроса с фронтендом

**Владелец:** Backend, затем Frontend. **Файлы:** [provider-pool.ts](../apps/api/src/ai/provider-pool.ts), [guide.routes.ts](../apps/api/src/routes/guide.routes.ts), [api.ts](../apps/tourist/src/lib/api.ts).

На одну провайдерную операцию сейчас отводится до 25 секунд. Фото → распознавание → ответ → TTS выполняются последовательно, поэтому общий запрос может длиться дольше 45 секунд, после которых frontend прекращает ожидание.

Ввести общий deadline HTTP-запроса и передавать оставшееся время/сигнал отмены во вложенные операции. Как только текст готов, его доступность не должна зависеть от долгого TTS: можно вернуть текст без аудио и использовать существующий `/api/audio/speech` для отдельной попытки. Конкретное поведение согласовать с frontend; простое увеличение всех тайм-аутов проблему не закрывает.

**Приёмка:** тест с искусственно медленными vision/text/TTS завершается раньше клиентского лимита; получение текста при отказе речи работает; при уходе со страницы дорогостоящие запросы по возможности отменяются; нет бесконечного loading. На настоящем запросе замерены полное время, модель и причина fallback без секретов и содержимого фото в логах.

### B04. Подготовить один настоящий HTTPS-адрес API и QR

**Владелец:** Backend/deploy + Frontend. **Основа:** [GIT_WORKFLOW_AND_DEPLOY.md](GIT_WORKFLOW_AND_DEPLOY.md), [env.ts](../apps/api/src/config/env.ts), [app.ts](../apps/api/src/app.ts).

Выдать команде адрес стенда и commit SHA. Настроить reverse proxy `/api`, PostgreSQL, разрешённые origins и серверные ключи. Заменить ключи из переписки; не передавать их через frontend env. Уже работающий чужой локальный mock на 4000 не считать настоящим API и не заменять без согласования с его владельцем.

Проверить IP-ограничения за реальным reverse proxy. Сейчас `trust proxy` не включён, поэтому все посетители могут делить IP прокси. Настраивать доверие только для известной схемы проксирования. Несколько инстансов потребуют общего хранилища лимитов; для одного демо-инстанса достаточно описать фактическую конфигурацию.

**Приёмка:** QR на телефоне через мобильную сеть открывает HTTPS без mixed content; браузер обращается к нужному API; ключей нет в JS, ответах и логах; рестарт сохраняет данные DB; лимиты дают понятный 429/503, а не ломают соседние запросы. Health-конфигурация дополняется реальным запросом, потому что `aiConfigured` не проверяет ключ онлайн.

### F01. Подключить национальный frontend к готовому плану

**Владелец:** Frontend. **Зависимость:** Backend подтверждает B04 и существующий контракт `/api/trips/generate`. Бэкендеру не нужно повторно создавать этот endpoint.

**Файлы:** [TouristHomeClient.tsx](../apps/tourist/src/components/TouristHomeClient.tsx), [api.ts](../apps/tourist/src/lib/api.ts), [journey.ts](../apps/tourist/src/lib/journey.ts).

Сейчас submit вызывает локальный `generateTrip`. Добавить HTTP-адаптер с валидацией response, отменой и тайм-аутом; использовать `trip` из ответа, сохранять `source`, `modelUsed` и причину fallback. Локальную генерацию оставить запасным вариантом с понятной отметкой. Англоязычные `warnings` сервера локализовать перед показом.

При восстановлении `readTrip()` сейчас заново рассчитывает поездку по сохранённому input. Для серверного плана это потеряет выбранный AI порядок мест. Сохранять и проверять сам полученный план вместе с происхождением; определить поведение при изменении версии каталога.

**Приёмка:** во вкладке Network виден реальный POST; UI показывает именно его места/суммы; refresh сохраняет порядок и источник; offline/429/503/невалидный JSON дают обозначенный локальный вариант без потери введённых данных. Проверены телефон, 4 дня, несколько городов и бюджет с дефицитом. Форматы денег: `budget` в долларах, расчёты в центах.

### A01. Проверить источники выбранного демо-маршрута

**Владелец:** Контент/AI + местный эксперт; Backend хранит утверждённые данные.

Для каждого показываемого объекта собрать конкретную ссылку/запись источника, статус «историческое утверждение / легенда / наблюдение», язык, дату проверки и проверившего. Для стоимости дополнительно: исходная валюта, за что платят, единицы тарифа, включение в общий билет и основание пересчёта в USD. Если цена не подтверждена, сохранять отметку об оценке.

Разобрать конфликты присланного JSON: Калта-Минор 1852/1851, Джума 212/213 колонн; согласовать alias Тош-Ховли и новый Islam Khoja. Не удалять существующий Пахлаван Махмуд из-за отсутствия в импорте. Не подавать смешанный текст истории как набор проверенных фактов.

**Приёмка:** у каждого показанного в демо утверждения и ценового значения доступно основание; легенда так и названа; общий UNESCO badge не заменяет источник конкретного утверждения. Утверждённый импорт и его версия отделены от исходного файла. Покрытие страны не выдаётся за проверенный каталог всех городов.

## Задачи PM и команды — не поручать бэкендеру как «ещё один endpoint»

1. Провести наблюдаемые проверки с целевыми самостоятельными путешественниками. Сохранить дату, профиль участника без лишних персональных данных, выполненную задачу, затруднения и подлинную обратную связь с согласием на показ. Число участников и результат указывать фактические; небольшая выборка даёт качественные сигналы.
2. Получить у одного местного партнёра конкретный следующий шаг: кто подтверждает контент, где/когда размещается QR, как набираются участники и кто собирает результаты. До договорённости называть статус переговоров, а не оплаченный пилот.
3. Зафиксировать выбранный трек, актуальный регламент и сценарий питча. Не заявлять процент победы или подтверждённый спрос на основании сборки и тестов.

## Общая приёмка на реальном стенде

| Шаг | Действие | Требуемое наблюдение |
| --- | --- | --- |
| 1 | Открыть QR с телефона через мобильную сеть | HTTPS-адрес и версия стенда записаны; ошибок mixed content нет |
| 2 | Выбрать Хиву + Бухару, 4 дня, $200, local/history, проживание | Реальный POST плана; `currency:USD`; источник виден; сумма равна слотам + резерву, дефицит не скрыт |
| 3 | Открыть один день и карточку места, обновить страницу | Порядок серверного плана сохранён; источник истории доступен; оценочные цены обозначены |
| 4 | Задать вопрос по Калта-Минору через `/api/guide/ask` | Ответ Groq; воспроизводимый Gemini WAV или явный текстовый режим; ID события подтверждён в DB |
| 5 | Отправить известное и постороннее фото | Верный ID для известного примера; неизвестное не становится первым объектом каталога |
| 6 | Открыть панель | Новое реальное взаимодействие отражено; seed не выдан за исследование/продажи |

## Что бэкендер возвращает команде

- Ветка/PR и commit SHA, изменения контракта и инструкция запуска/схемы.
- URL стенда и ожидаемые origins; секреты через серверную конфигурацию, не в сообщении или репозитории.
- Результаты B01–B04: что проверено, на какой среде, какие пункты ещё открыты.
- Пример plan response с метаданными и обезличенный ID настоящего guide-события; подтверждение чтения из DB/панели.
- Замеры полного времени запроса и поведение при 429/недоступной речи/DB; отсутствие seed в реальных метриках.

В общий отчёт о приёмке внести фактические результаты, не проставлять чекбоксы заранее. Пока B01–B04, F01, A01 и телефонный прогон не закрыты, состояние продукта — серверная AI-заготовка и работающий локальный frontend, а не подтверждённый сквозной пилот.
